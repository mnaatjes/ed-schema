# Master Risk Register

Barry Boehm Risk Exposure ($RE = P \times I$) log and Environmental/Technical boundary definitions for the `ed-schema` project lifecycle.

---

## 1. Environmental and Technical Boundaries

The operational envelope of `ed-schema` is strictly bounded by the following environmental and architectural realities:

* **Pure Shared Library Execution (In-Process Invariant):** Must operate strictly within the caller's Python interpreter across Linux (desktop / server), Linux Steam Deck (Proton / Steam runtime), and native Windows NT. Zero execution of external shell commands, background daemons, or subprocesses during runtime validation or compilation.
* **Microsecond Runtime Latency Ceiling:** In-memory registry lookup and pre-flight validation must execute in microseconds ($\le 50 \mu\text{s}$) to avoid introducing latency into real-time telemetry streaming pipelines.
* **Zero Business-Logic Knowledge (Total Domain Model Decoupling):** Must maintain complete ignorance of Elite Dangerous game entities (stars, planets, ships, modules, commodities, journals). `ed-schema` operates strictly on abstract schema metadata, ASTs, and dictionaries.
* **Standards-Compliant JSON Schema Baseline:** Ingestion and validation are strictly bounded to standard Draft-07 and Draft 2020-12 specifications.
* **Deterministic Build-Time Invariant:** Code generation occurs strictly at development or pre-commit time. Zero runtime dynamic evaluation (`eval()`, `exec()`, or dynamic `type()`) is permitted.
* **Multi-Namespace Provider Isolation:** In a unified `ed-connectors` architecture ([RFC 0001](file:///home/michael/src/github.com/mnaatjes/ed-schema/architecture/rfcs/0001_fleet_unification_and_provider_subpackage_architecture.md)), schemas from different API providers (`capi`, `eddn`, `inara`, `spansh`) must remain strictly isolated without key or class collisions.
